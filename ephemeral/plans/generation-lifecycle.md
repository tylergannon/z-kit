# Initial generation, publication and cache design

These decisions elaborate the [build brief](mapping-contract.md), not a separate implementation request. Publication and cache correctness belong to the first generator slice; a broad retained-worker or performance project does not. No behavior described here has been implemented or tested in Type Projector.

## Phase boundaries

Keep build configuration declarative. Compile a dedicated host generator importing the model and explicit application-target settings; execute it through tracked build Run steps. Configuration reuse can skip the build function, so writing generated files there is incorrect. Target-sized native types must retain application-target meaning even though the generator runs on the host.

Keep native type/field associations in the internal mapping so codecs can read and construct native values. Foreign backends consume that mapping inside this project. There is no requirement to expose a public grammar, plugin API or third-party backend SDK.

Generation returns a complete requested artifact set before publication changes destination files. A cached artifact bundle and its identity are distinct from the live destination directory. The publication/check stage must still inspect that directory when generation is reused; an entirely cached Run step must not hide destination drift.

## Identity and reuse

Use a versioned canonical encoding of the reachable mapping for semantic fingerprints. Include roots, fields, presence policy, enum/union labels, numeric widths, descriptions, canonical wire names, application target and every output-affecting backend/version/option. Encode recursive references with deterministic traversal identities, not native pointer bytes or a depth cutoff. Destination paths select publication locations rather than changing the semantic model.

Use ordinary Zig compilation/build caches first. A semantic hit need not eliminate reflection or lowering; it must eliminate neither validation nor destination checks. A separate persistent store or retained compiler worker needs evidence of value before adding a new lifecycle. Body-only edits may rebuild native inputs but should not change generated bytes; shape, description, target, naming and output-option edits must not reuse incompatible artifacts.

## Ownership and publication

An ownership manifest records relative output paths and their last published content hashes. Reject unsafe paths and collisions with unowned files. Treat externally edited managed outputs as conflicts instead of silently replacing them; automatic damaged-file repair and a force-overwrite mode are not initial requirements. Missing desired outputs can be generated normally. Remove stale outputs only when their bytes still match the recorded owned version; preserve/report edited orphans.

Preflight the artifact set and ownership conflicts before mutation. Compare bytes and preserve equal files and mtimes. Check-only reports drift without modifying outputs or ownership state. It must also detect removals and missing files, not just changed file contents.

Atomic replacement is per file, not a whole-set transaction. Make partial publication resumable: retain the planned old/new hashes and staged bytes until the ownership manifest is committed. Recovery can recognize either planned version and finish; unexpected bytes remain a conflict. Check-only reports pending publication instead of resuming it. Serialize publishers for the same output root. Report the paths actually changed on failure. This avoids treating our own interrupted publication as an external edit on the next run; exact manifest/staging representation is an implementation detail.

The first example should demonstrate normal generation, an unchanged rebuild, input invalidation, missing output, owned stale removal, unowned/edited conflicts, check-only drift and an interrupted/retried publication. These are witnesses for the brief's generation rules, not a demand for an exhaustive filesystem corpus or a timing target.
