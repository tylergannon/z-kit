# z-kit build baseline

The product goal is **a usable Zig backend for ordinary SvelteKit applications**. The project and repository name is **z-kit**. The projector is supporting machinery; completing a standalone declaration generator is not, by itself, bringing z-kit online.

Status: **accepted product scope and internal projector placement**, per the user’s approval on 2026-10-25, with subsequent feature ordering and scope/proof limits recorded in the [feature specification](first-application-spec.md). The milestone assignments below describe larger product outcomes; they do not add gates to the first feature. The [mapping brief](../../modules/projector/ephemeral/plans/mapping-contract.md), verified configuration experiment and deferred generation design remain component references.

## Decision: one product, internally modular

Build the projector as a lightweight source module inside z-kit, with one app-wide generation pipeline. Keep its reflection/mapping/codecs independent of routing, HTTP, Vite and the renderer. An app can use native mapping/schema helpers without constructing a web server. Preserve the verified `Projection(T)` authoring shape in [`modules/projector`](../../modules/projector/README.md). One root build owns the internal source module; there is no separate projector package or release. A future application-facing import path is not fixed here.

| Placement | What becomes easier | Cost / condition |
| --- | --- | --- |
| Internal z-kit module — selected | Handler signatures, route events, wire roots, JS/TS bindings and publication evolve in one checkout/release. One owner sees the whole application graph. | Requires deliberate internal dependency direction; avoid a monolithic generator/runtime tangle. Extract later if a real independent consumer needs it. |
| Separate projector repository | Independent release/use outside z-kit; a small source dependency can still specialize over app types. | Cross-repo API/version coordination and paired changes remain. Prefer this if an actual compile/build experiment shows the boundary simplifies integration, or an independent customer justifies it. |

This is a coordination/ownership simplification, not a demonstrated compiler-speed improvement. Zig source modules and comptime specialization work in either placement. Moving files into one repository does not merge the separate semantic contexts of a host generator and target application. No separate public grammar/plugin SDK is required. Keep the shared Go/Zig **devalue runtime** as its existing independent protocol dependency; embedding the projector does not mean copying that runtime.

## One pipeline and the bootstrap constraint

The design must break dependencies in this order:

1. Obtain Kit route/matcher/module metadata; choose application target and native route declarations.
2. Generate the route/event types that native handlers import, plus an import registry for known handler modules. Do not require compiling handlers against files that only their own later reflection would create.
3. Compile/run the host generator over those handlers; reflect signatures, collect one shared wire-root graph, and emit bindings, stubs, native registration information and identity metadata together.
4. Build Kit/Vite with those bindings. A separate native prerender helper can answer build-time operations without importing final embedded frontend assets.
5. Compile the target application using the completed frontend artifacts and native codec specializations. Development uses Vite rendering with the same native application semantics.

This is the key integration work to prove before a large standalone-projector sprint. Internal placement makes its ownership simpler but does not automatically solve the cycle. Explicit registries/import generation are viable Zig mechanisms; global reflection over arbitrary undiscovered application declarations is not assumed. Normal source imports/comptime remain the starting point; no compiler fork or type-introspection server is required.

## First application proof and early decisions

The [feature specification](first-application-spec.md) records the user's construction direction: the initial foundation includes `zkit new` wrapping upstream SvelteKit creation, empty/examples starter choices, and a real app with Vite listening on a Unix domain socket behind the Zig proxy. The repository example demonstrates the development-server portion, and [fresh application evidence](../proof/new-app/README.md) demonstrates creation and independent build/start with explicit local framework dependencies. Then progressively select useful features, with remote functions, page loads and backend reloads as the current preferred progression. Each feature must also work in a freshly generated examples application, while the empty starter remains runnable. The product checkpoint below is a larger outcome, not the first feature to build.

Resolve the initial development target and native HTTP/std.Io composition before implementing the trivial development server. Resolve handler declaration/discovery before native operation integration, and the production target/engine/packaging path when taking up the compiled application. These are unresolved choices; the selected source-module placement does not settle them. App-specific databases, authentication providers and workflow engines remain application code, supported by the framework's request, cookie, data and lifecycle APIs.

The first product checkpoint is **one z-kit app in a browser**: a matched route with a server load, a typed query and command, a cookie/locals effect, SSR hydration and client navigation. A native shape edit must regenerate compatible bindings; a body edit must reach the browser after rebuild; invalid code must show a useful error and recover. Reuse this one app for publication/cache witnesses rather than building a second acceptance framework.

Call that *development-online* until production is separately demonstrated. When the compiled-application feature is selected, qualify the proposed engine through the same real Kit example: async render, native fetch callback, headers/first body bytes before producer EOF, and abort/cleanup for the supported behavior. Engine selection and qualification are not prerequisites for the trivial development server, first remote, page load or backend-reload feature. This replaces the earlier instruction to qualify an engine before broad generation work. Development need not link the production engine.

Then make the same example deployable as a native application with embedded frontend output. Expand forms, layouts, live streams, prerender and custom transports according to actual customer paths. Generic JSON codecs need not wait on an A/B code-emission experiment, but schema/provider/enum/time features remain deferred until their customer milestone; this inventory does not silently reverse those decisions.
